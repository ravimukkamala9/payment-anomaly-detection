A three-tier answer to 9,600 possible failure modes

How a five-week synthetic decline dataset validated a monitoring design that finds a rate spike, a masked shift, and a low-volume break — without pre-building a single monitor for any of them.

The data foundation

6.89 million individual transactions, compressed at every stage

The 52,920 figure is not a transaction count — it is the number of aggregated (hour × cell) rows. Each row's total_count column holds the actual individual transactions attempted in that hour, for that context. Summed across all 52,920 rows, five weeks of history represent 6,890,626 individual transactions, of which 96,429 declined. In the single current window — Monday 14:00 — that's 17,658 individual transactions across the 63 active cells, 405 of them declines.

No cell list is hand-maintained. A GROUP BY on the seven dimension columns, run against the raw data with zero prior knowledge of what exists, rediscovers the same 63 cells. Cost tracks real traffic, not the theoretical combination space — a schema that technically allows 9,600 combinations still only ever materializes rows for the ones that occur.

Historical comparison method

Every one of the 63 cells is judged against its own history

The current window — week 0, Monday, 14:00 — is compared to the same day-of-week and hour in weeks −1 through −4. Four historical points per cell set a mean and standard deviation; the current point's distance from that mean, in standard deviations, is the z-score every stage is built on. A cell with no history at all is flagged outright (z = 99) rather than ignored.

Each stage below runs as two plain queries — current window, then historical window — with no join between them. Aggregation stays in SQL; the mean, standard deviation, and z-score are one small computation downstream, in whatever layer already holds both result sets.

Design choice, not a fixed pipeline — once the two queries return, scoring is swappable. This brief uses z-score throughout; the same current-window and historical-window result sets feed equally well into an isolation forest or local outlier factor model if the cell population gets large enough, or noisy enough, that a univariate threshold stops being trustworthy.

Stage 1

Roll-up WoW z-score — 63 cells collapse to 18 monitors

Cells are summed by decline code × channel only, discarding network, geography, entry mode, purchase type, and auth type. Cheap, coarse, and the first line of defense — it catches a spike large enough to survive being diluted across every other row in its bucket.

SQL — query 1, current window

SELECT decline_code, channel,
       SUM(total_count) AS total,
       SUM(decline_count) AS declines
FROM raw_declines
WHERE week = 0 AND day_of_week = 0 AND hour = 14
GROUP BY decline_code, channel;
-- 18 rows: one per (decline_code, channel) monitor

SQL — query 2, prior 4 weeks, same slot

SELECT week, decline_code, channel,
       SUM(total_count) AS total,
       SUM(decline_count) AS declines
FROM raw_declines
WHERE week > 0 AND day_of_week = 0 AND hour = 14
GROUP BY week, decline_code, channel;

Stage 2

Contribution shift — two queries, all 63 cells, no monitor list

Instead of a rate, each cell's share of the window's 405 total declines is compared to its own historical share. Because share is zero-sum, three cells absorbing a disproportionate slice forces every other cell's share down — even when nothing changed in its own volume.

SQL — query 1, current window

SELECT network, geography, entry_mode, purchase_type, auth_type, channel, decline_code,
       SUM(decline_count) AS decline_count
FROM raw_declines
WHERE week = 0 AND day_of_week = 0 AND hour = 14
GROUP BY 1,2,3,4,5,6,7;
-- 63 rows: one per active cell. Divide each by the column sum for contribution_pct.

SQL — query 2, prior 4 weeks, same slot

SELECT week, network, geography, entry_mode, purchase_type, auth_type, channel, decline_code,

Stage 3

Full-granularity WoW — every cell judged alone

No roll-up, no shared pool. Each of the 63 cells is compared only to its own four-week trail at the same day and hour. This is the only stage where a cell's own decline rate, not an aggregate or a share, is the basis for the alert — and the only stage where all three injected anomalies register with maximum separation from noise.

SQL — query 1, current window

SELECT network, geography, entry_mode, purchase_type, auth_type, channel, decline_code,
       total_count, decline_count
FROM raw_declines
WHERE week = 0 AND day_of_week = 0 AND hour = 14;
-- 63 rows: every active cell, no roll-up, no aggregation

Worked example

One cell, two opposite verdicts

MC × DOMESTIC × EMV × DO_NOT_HONOR appears in both Stage 2's and Stage 3's alert list this window — with opposite signs. Both are correct. They answer different questions from the same 11 declines.

405 only exists because Stage 2 needs a whole-window denominator — it's the sum of every row's declines, so it moves whenever any cell moves. 564 never leaves this one row — it's this cell's own transaction count, untouched by what the other 62 cells do. That's the entire mechanical reason the two stages can disagree on the same 11 declines.

All three anomalies were caught by every stage in this dataset — a property of how sharply they were injected, not a guarantee. The design reasoning holds independent of that: Stage 1 is cheap insurance against large spikes, Stage 2 catches share shifts a rate-only view would miss, and Stage 3 is the only stage that isolates a low-volume cell from any pooling effect at all.

Bottom line

No stage requires knowing in advance which of the 9,600 theoretical combinations will matter. All three discover their working set — 18 monitors, 63 cells, 63 cells — directly from what the current window's data contains, then spend their statistical budget only on what showed up.
